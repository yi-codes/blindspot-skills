# 独立截图评审回路

> 这一页补的是 `designlib check` 查不到的那一半：lint 能证明"该有的字段都有"，
> 证明不了"这张页面成不成立"。它需要一个**看结果的**角色，而不是写它的那个。

---

## 为什么需要

`principles.md` §10 已经写了：lint 通过 ≠ 设计成立。但那句话只说了"还差什么"，没说由谁补。

执行代理评不了自己的作品。它同时背着代码结构、实现成本、之前写过的理由和"跑通了"的满足感，
所有信息都在把它往"再修一点就好"推。这不是模型不诚实，是**上下文污染**：
它已经知道答案是怎么来的，就不可能再像第一次看见那样看。

所以评审必须来自**一个没有这段记忆的新上下文**。

这一页把评审做成固定动作：给它什么、不给它什么、按什么判、跑几轮、什么时候停。
判据全部复用库里已有的硬规则，不另起一套"好不好看"的主观标准。

---

## 输入边界（最重要的一条）

**只给四样东西**：

1. 真实运行环境里截的图（主视图 + 与本次变化相关的状态；桌面与窄屏各一张）
2. 目标用户与主要任务，一两句话
3. 这份设计要传达的 brief（选定方向的视觉隐喻、目标感受、必须避免的元素）
4. 必要的参考图（质量基线，不是临摹目标）

**绝对不给**：

| 不给 | 原因 |
|---|---|
| 代码、token、实现细节 | 会让评审开始评估"写得对不对"，而不是"看起来对不对" |
| 实现难度、工期、历史解释 | 会诱导它替约束找借口、放水 |
| 上一轮的评分和意见 | 会锚定，评分失去相对可比性 |
| 目标分数 / 停止条件 | 评审为了让流程结束会给高分 |
| 用户说过的偏好原文 | 那是要靠 brief 翻译过的，原话会让它复读而不是判断 |

**参考图只当基线不当答案。** 有多张可比参考时，让评审按完成度**匿名排序**并解释排序依据，
比"打几分"稳定得多。

## 评审量表（复用既有判据，不新造）

评审按下面五组逐项看，每组只报**确实出问题**的项，不写赞美。

| 组 | 出处 | 看什么 |
|---|---|---|
| 六层合格线 | [`LAYERS.md`](../LAYERS.md) | 第 1/2 层取值是否走 token；第 3 层状态是否齐（default/hover/focus/active/disabled/error/open）；第 4 层光源能否指认、阴影有无偏移、主分隔手段是否唯一；第 5 层 logo/图片/背景/图标有没有按参数执行；第 6 层焦点环、展开态、reduced-motion |
| 一眼假 12 条 | `principles.md` §11.2 | 紫蓝渐变、eyebrow 小字、拉开字距的全大写标签、中点拼元信息、三列等宽图标卡、氛围光、装饰性文字、同一件事说四遍…… |
| Specificity | `principles.md` §11.1 | 遮住产品名，这份设计还属于这个产品吗？站得住 = 模板 |
| 光源 / 材质 | `principles.md` §12 | 能指认光源的渐变是材质，指认不出的是气氛 |
| 可用性与降级 | `SKILL.md` The Floor 第 6/8/10 条、§5 媒体纪律 | 中文行高、深色字重、焦点可见、窄屏、对比度、素材没加载时主任务能否完成 |

**不要问"它漂亮吗""像不像 AI"。** 这两个问题每轮的答案都会漂移，是评论区实测过的失败模式。
问的是"哪条规则被违反了、违反在哪一块、最小修法是什么"。

---

## 固定提示词

每轮用**同一段**，不改字。改了，分数就不再可比。

```text
你是一位独立的设计评审。你只拿到截图、目标用户与任务、审美 brief 和参考图。
你没有代码、没有实现说明、没有历史意见，也不知道任何目标分数。

按这个顺序做：

1. 用一句话说出这份设计在追求什么视觉方向。
2. 想象一家顶级设计工作室会怎么执行同一个方向，把那个完成度当作基线。
3. 对照基线，找出差距最大的 1–3 个具体问题。逐个说明：
   - 出问题的位置和现象（不要笼统说"层级不清"）
   - 它违反了下面哪一条判据
   - 最小的修法（能一步改完的不写三步）

判据清单：
- 六层合格线：变量/排版/组件状态/材质体积/标识图像/动效交互
- 一眼假 12 条：紫蓝渐变、标题上方宣布型小字、拉字距全大写标签、
  中点拼元信息、三列等宽图标卡、无偏移发光、装饰性文字、事实重复四遍等
- Specificity：遮住产品名还站得住吗
- 光源：渐变能不能指认出来自哪儿
- 可用性：中文行高、深色字重、焦点可见、窄屏、对比度、素材降级

额外要求：
- 判断整体结构，也判断细节
- 对模式化、一眼能看出是默认生成的东西要扣分
- 反馈要短、具体、可操作，不写感受式长文
- 明确、有观点，不要模棱两可

最后给一个 1–10 的相对完成度信号，并说明它是相对哪一轮、哪个基线。
这个信号只用来观察是否收敛，不构成质量认证或上线许可。
列出每个问题、所在位置、最小修法。不要改代码，也不要重写设计。
```

## 循环纪律

1. 执行方按优先级**只改最影响效果的 1–3 个问题**，其余记下但不顺手改。
2. 重新截图（同样的视口、同样的状态），用**同一段提示词**再评一轮。
3. **最多两轮。** 两轮后若主要问题反复、信号不上升，停下来报告剩余缺口，
   由人决定是否换方向 —— 不要无限追分，也不要让两个 Agent 互相拉扯。
4. 每轮结束分开写两段：**审美评价** 与 **功能验证**。
   有截图只证明"看到了视觉"，不证明交互、性能、无障碍、刷新后读回、保存失败这些行为正常。

### 关于 9/10

- 它可以作为执行方**内部**的愿景，但**不写进评审提示**（写了评审就会为了收尾放水）。
- **不进 `lint.py`，不进 build，不作为验收门槛。** 库里已经有
  "lint 通过 ≠ 设计成立"，再叠一个主观分数只会让产出变成一个不可比的数字。
- 同一张图在不同会话里分数会漂。它只是**同一评审、同一提示词下的相对信号**，
  不能跨任务、跨模型比较，也不能写进交付报告当结论。

## 能力不可用时的降级

| 缺什么 | 怎么办 |
|---|---|
| 没有可委派的子 Agent | 按同一量表自查，并在交付里明确写"这是自查，不是独立评审" |
| 拿不到运行环境截图 | 标注"视觉验证未完成"，**不要依据代码宣称效果良好** |
| 没有参考图 | 用 `styles/<slug>/DESIGN.md` 的 Do/Don't 与 Known Gaps 当基线，说明基线来源 |
| 只有一张截图 | 只评这一张，注明"窄屏与状态未覆盖"，不要外推 |

**降级要写出来。** 隐瞒"这次没看图"比没看图本身更糟，因为它会让下游把没验证的东西当成已验证。

---

## 记录

每轮评审留下三样，放进本次任务产物，**不进长期记忆、不进风格的 `DESIGN.md`**：

- 截图（含视口与状态标注）
- 评审输出原文
- 本轮改了哪 1–3 项、改完重截的图

理由和 `scripts/explore.py` 的种子一样：这是**一次性判断燃料**，不是风格属性。
风格文档里只沉淀能被复用、能被 lint 检查的规则。
