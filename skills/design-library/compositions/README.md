# Compositions · 页面构图骨架层

> 风格回答"它长什么样"，构图骨架回答"信息怎么站队"。
> 两者正交：同一个骨架可以套任意风格，同一个风格也要靠不同骨架承载不同任务。

---

## 为什么有这一层

`styles/` 把色、字、距、圆角、材质、组件形态做成了严格契约，但它刻意不管
"这一屏谁先被看到、侧栏为什么在这、密度往哪压"。结果是拿到真实任务时，
这部分仍要临场发明——而它恰恰是页面成不成立的大头。

`preview/_frame.css` 里已经沉淀了一批 `frame-*` 结构类（`frame-app`、`frame-side`、
`frame-story`、`frame-grid`、`frame-docs`、`frame-data-shell` 等）。它们一直在用，
但从未被当成可命名的资产。这一层把它们**提炼、命名、写清使用条件**，让构图
从临场发挥变成可选、可比、可复用的决策。

---

## 它和风格的关系

| | styles/ | compositions/ |
|---|---|---|
| 回答什么 | 长什么样 | 信息怎么站队 |
| 固化在 | `tokens.css` | `frame-*` 结构类 + 本文档的骨架定义 |
| 正交性 | 一种风格可配多个骨架 | 一个骨架可套多种风格 |
| 谁先定 | 后定 | **先定** |

组合顺序永远是：**先选骨架，再选风格，最后套 token**。
先选风格会让骨架迁就配色，是本末倒置。

---

## 一个骨架必须写清什么

每个骨架是一个独立 `.md`，必填以下六项：

1. **适用任务**：什么用户要完成什么事时用；给出具体例子，不写形容词。
2. **主角与视线**：这一屏唯一的主角是谁，视线从哪到哪，第一眼落在哪。
3. **网格与密度**：栏数、比例、间距来源；密度是 sparse / medium / dense 哪一档。
4. **挂载点**：用哪些 `frame-*` 类，每块挂什么组件，空态/错误态落在哪。
5. **与风格的咬合**：骨架只定结构，视觉一律走所选风格的 token；说明哪些
   `family` / `tier` 风格适合，哪些会打架。
6. **禁用项**：什么任务不能用，用了会出什么问题。

---

## 入库门槛

- 必须能在 `preview/_frame.css` 找到对应结构类，或在骨架文件里给出新增类的
  完整 CSS（不写"大概是两栏"这种空话）。
- 必须有一个真实 preview 页作为活样例，链接到 `preview/<slug>.html`。
- 密度必须是三档之一，不能含糊。
- 禁用项至少两条，且是具体的失败后果，不是"视情况而定"。

纯文字描述、没有结构类、没有活样例的，不算骨架。

---

## 咬合清单：结构层会覆盖风格 token

`preview/_frame.css` 是结构层，但它写了几条**视觉默认值**，会压过风格 token。
2026-11-28 用 `tide-station` 四页样张实测发现，套骨架时必须在页面侧显式钉回：

| 现象 | 根因 | 处理 |
|---|---|---|
| 卡片 `h2` 塌成正文大小 | `.frame-grid h2 { font-size: 1rem }` 压过风格字阶 | 页面侧用 `var(--<前缀>-text-xl)` 重设 |
| 深底上正文发灰 | `.frame-task p` 等带 `opacity: .78`，叠加风格 muted 色二次削弱 | 钉回 `opacity: 1`，中文提到正文级字号 |
| 主按钮变成空色块 | `:where(a)` 的 accent 字色与 `.ds-btn-primary` 背景同色 | 页面侧把链接按钮的 `color` 钉回 `var(--<前缀>-canvas)` |
| 侧栏次要信息消失 | `.frame-muted { opacity: .68 }` 叠加深色 token | 钉回 `opacity: 1`，改用 `ink-muted` 而非 `ink-faint` |

**规则**：结构层只负责栏、间距、对齐；一切颜色、字号、字族、透明度以风格 token 为准。
遇到冲突时页面侧显式覆盖，并把该条补进骨架文件的「与风格的咬合」一节。
这条不是审美建议，是"lint 全绿但页面读不了"的实际来源。
